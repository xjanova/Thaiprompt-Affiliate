💡 Key Design Decisions · ตัดสินใจสำคัญทางสถาปัตยกรรม

1. ChannelManager pattern — แยก channel-specific code (FB vs LINE vs API) ออกจาก business logic ทำให้ FortuneConversationService ใช้ logic เดียวกันได้ทุกช่อง.
2. Trait-based state machine — FreeCardConversationTrait + ProSessionTrait + CelticCrossConversationTrait + PayFirstGateTrait แยก concern ตาม tier.
3. Pool-first AI — AiApiKeyPoolService เลือก key ตาม purpose + preferred provider ก่อน fallback ไป settings (single source of truth).
4. Queue-based AI calls — ทุก AI request ผ่าน ProcessFortuneTelling job (retry 3 ครั้ง + exponential backoff) เพื่อป้องกัน webhook timeout (Facebook จะ disable หากเกิน 200 response).

📋 7-Step Linear Pipeline

1
User Sends
ลูกค้าพิมพ์ "ดูดวง" หรือกด Quick Reply ผ่าน Facebook Messenger / LINE OA / Mobile App
2
Webhook Verify
ตรวจ signature (HMAC-SHA256), return HTTP 200 ทันที, push event เข้า queue
3
Anti-Spam Guard
เช็ค rate limit, prompt injection, rapid-fire flood, repetitive — pass หรือ silent mode
4
State Machine
ConversationService อ่าน state ปัจจุบัน (NEW/COLLECTING_BIRTHDATE/PENDING_PAYMENT/...) แล้วเลือก action
5
Payment Match
SMS Checker หรือ Stripe webhook → FuzzyMatcher จับคู่ unique_amount → mark is_paid
6
AI Generation
Queue worker ดึง key จาก Pool (purpose-based) → call provider → save response + tokens
7
Deliver + Comm
ส่ง message แบ่ง chunk (2000 ตัวอักษร) → trigger commission → upsell Quick Reply

🎯 Why Unique Decimal Amounts? · ทำไมต้องใช้เศษทศนิยม?

ระบบสร้าง unique_amount ต่อบิลด้วยการสุ่มทศนิยม (เช่น 39.01, 39.02, 39.07...) เพื่อให้ SMS Payment Checker สามารถจับคู่ SMS จากธนาคารกับบิลที่ถูกต้องได้ แม้ในกรณีลูกค้าหลายคนโอนพร้อมกัน — ทศนิยมคือ fingerprint ของบิล. ถ้าโอนผิดยอด (เช่น โอน 39.00 แทน 39.07) ระบบจะ ไม่จับคู่อัตโนมัติ — ต้องให้แอดมิน assign manual.

ใหม่: AiApiKeyPoolService เป็น single source of truth — admin จัดการ Pool ที่เดียว ไม่ต้องตั้งซ้ำใน 2 ที่. Pool ว่าง → fallback ไป settings (backward compat).

Fuzzy Matcher Logic

PaymentFuzzyMatcher.php
  • amount tolerance ±0.01 บาท
  • time window (30 นาที backward)
  • sender name similarity (Levenshtein)
  • confidence score 0-100
  • threshold 80% → auto-link

Floating Bills

Manual review queue
  • SMS เข้าแต่ไม่ match user หรือ bill
  • เก็บใน FortuneReading + is_floating=true
  • FCM แจ้ง admin app ทันที

Stripe Webhook

FortuneStripeWebhookController
  • endpoint: POST /webhook/fortune-stripe
  • verify Stripe signature
  • handle: payment_intent.succeeded
  • auto-link by metadata.bill_reference
  • FortuneStripeService idempotency
💡 Why decimal-based matching?

ปกติแล้ว SMS ธนาคารไม่ส่ง metadata ของบิลกลับมา — มีแค่จำนวนเงินกับชื่อผู้โอน. ระบบจึงใช้ unique_amount (เช่น 39.07, 39.13, 99.23) ที่สร้างเฉพาะต่อบิล ทำให้ amount = bill ID โดยปริยาย. วิธีนี้ ไม่ต้องพึ่ง Payment Gateway — ใช้ได้กับทุกธนาคารที่ส่ง SMS notification (PromptPay, KBANK, SCB, BBL ฯลฯ).

// section.14 — design decisions

Critical Design Decisions

ทำไมระบบถึงออกแบบแบบนี้ · trade-offs ที่เลือก

🎯

Pay-First Warning, Not Block

2026-05-03 · refactor v1 → v2

ก่อน: มีบิลค้าง → block ทุก service

ใหม่: เตือนใน reply แต่ยังให้สร้างบิลใหม่ได้ — เพิ่มอัตราการ recover บิล

🔄

Reduced Required Questions

3 → 1 questions

ก่อน: ต้องการ 3 คำถาม → ลูกค้าหลายคนเลิกกลางทาง

ใหม่: 1 คำถามเพียงพอ — focus ลึก แม่นกว่า

⚡

Relaxed Rapid-Fire Threshold

6 → 20 msgs / 15s

ก่อน: 6 msgs/30s trip silent mode — บล็อก legitimate flow บ่อย

ใหม่: 20 msgs/15s — จับเฉพาะ real flood

🌐

Pool-First, Settings-Fallback

2026-05-13

ก่อน: ตั้งใน 2 ที่ (Pool + Settings) สับสน

ใหม่: Pool เป็น single source of truth — settings fallback เท่านั้น
